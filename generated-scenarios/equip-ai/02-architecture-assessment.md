### Storage, query and expiry design

Hot block blobs minimize cost for this batched two-hour stream without a minimum-capacity database.
Cool, Cold and Archive have 30/90/180-day minimum retention economics and do not fit short-lived frequently read data.
Table Storage is cheap for keyed access but adds per-event writes/deletes and an indexing/expiry worker.
Cosmos DB's native TTL does not justify its database cost for this bounded read-only reference.
Hot Blob is the lowest-complexity low-cost candidate, not a proven universal price minimum.
Reprice against actual query frequency before a production rollout.

At 1,000 devices/minute, four initial IoT partitions and 60-second flushes give roughly 5,760 nonempty blobs/day,
versus 1.44 million per-event objects/day. Actual routing batches and pricing remain measurable assumptions.
Never send raw two-hour history to the model. Aggregate in code and return at most 20 equipment summaries per tool.
Require narrower scope or pagination for larger result sets; explicitly label partial results.

List only relevant UTC hour prefixes plus bounded clock-skew overlap.
Allow at most 1,024 blobs and 128 MiB per retrieval, eight concurrent reads, and reject oversize queries explicitly.
A single-flight, 30-second in-memory parsed-data cache avoids five duplicate fleet scans.
Limit the cache to a conservative 512 MiB allocation budget and expire/filter observations on every use.
The implementation reserves 256 MiB for buffers and charges strings, records and index overhead before retention.
This bounds estimated cache allocations, not total process working set; measure actual process memory after deployment.
Cache no model answers.
Apply per-user site filtering before tools, citations or downloads leave the API,
even when the internal cache is shared.
If limits/latency fail at the stated envelope, report measurements and revise indexing, not return fake completeness.

Use observation time for business validity, with future-skew and trusted envelope enqueue-time checks.
Payload site claims never determine access. Read routed envelopes, not just assumed raw event bodies;
validate the connection device ID and handle/document JSON/base64 representations explicitly.
Deduplicate event/message identity across replayed batches; do not let an older sequence overwrite newer state.
Invalid data yields a counted warning and explicit coverage status, not a silently healthy machine.

Physical cleanup uses age of the blob's latest possible valid event, not creation time alone.
Delete only fully expired batches, use ETag conditions, retry conflicts later, and never delete a current writer's blob.
IoT buffers can retry late batches; old observations remain invalid and cleanup reclaims late material promptly.
The five-minute cleanup schedule targets deletion by 130 minutes when healthy; outages extend physical retention.
Blob lifecycle's periodic runs are not an hourly TTL mechanism.
No soft delete, versioning, snapshots, immutability or backup for the volatile container.
Static equipment metadata can persist; it contains no volatile sensor history.
Log only timing/count/status and non-sensitive correlation identifiers with a documented 30-day diagnostic retention.

Broker/service buffers can exceed two hours. The built-in Event Hubs-compatible IoT endpoint has a minimum one-day
configured retention; native route retry storage is also service-managed. Do not promise universal two-hour erasure.
No separate Event Hubs-compatible consumer is planned: current IoT documentation says its built-in endpoint needs SAS,
whereas the selected managed-identity Blob route avoids service connection-string secrets entirely.
