### Story and synthetic identity provenance

Adatum Corporation operates an engineering equipment-support function covering machinery in Seattle, Tacoma,
Everett, Spokane and Yakima. Operations staff currently compare device dials and dashboards to answer support calls.
The proposed interface answers questions such as "Which Tacoma machines have rising vibration in the last 30 minutes?"
with measured values, timestamps, units, missing-device warnings and links to the authorized evidence.
It provides a triage explanation, not a machine-control command or an authoritative mechanical diagnosis.

Device events have `schemaVersion`, `messageId`, `deviceId`, `observedAtUtc`, `sequence`, `temperatureC`,
`vibrationMmPerSecond`, `pressureBar` and `operatingState`.
IoT Hub's authenticated connection device ID is authoritative; reject a payload device ID that disagrees.
Resolve site and equipment ownership from the trusted inventory, not the payload.
Validate finite measurements, range, schema, UTC time and future clock skew of at most two minutes.
Deduplicate by device/message identity before aggregation; late data cannot replace a newer current reading.

Tool requests carry explicit equipment/site IDs and a bounded UTC window of at most 120 minutes.
Tool results include `status`, `asOfUtc`, `windowStartUtc`, `windowEndUtc`, `evidenceIds`, `coverage`, `warnings`
and deterministic metric summaries. The authenticated principal's site entitlements are supplied out of band.
Validate them on every tool invocation and evidence-download request, never through model instructions alone.

## Non-Functional Requirements (NFRs)

| Requirement | Target | Acceptance evidence |
| --- | --- | --- |
| Freshness | Exclude age >= 120 minutes at tool execution and final response validation | Clock-boundary tests |
| Current status | Readings older than five minutes are stale | Stopped-device fixture |
| Ingest latency | Routed measurement visible within 120 seconds in normal operation | Live device-to-app trace, later |
| Response latency | p95 <= 30 seconds; five users | Local query measurements; later live agent test |
| Burst tolerance | 50 events/second for 60 seconds; no missing unique events | Later authorized ingestion test |
| Bounded retrieval | Max 128 MiB, 1,024 blobs, eight concurrent reads | Limit, cancellation and oversize tests |
| Deletion | Five-minute cleanup; delete by age 130 minutes when healthy | Expiry and outage/recovery tests |
| Isolation | Local session, server-assigned role and site enforced before evidence leaves tool | Session and tool tests |
| Availability | Explicit dependency/cleanup failure; no fake success | Negative tests and health signal |
| Cost | No minimum-throughput database; batch ingestion and on-demand inference | Transparent planning estimate |
| Safety | Advisory support only; no actuation or automated repair | Absent write tools; rejected control prompt |

Two hours is a **business freshness window**, not a guarantee of irreversible deletion from every Azure subsystem.
Broker retry buffers, service-managed model processing and operational metadata can persist longer.
Blob deletion is asynchronous and outage-sensitive.
No backups, versioning or soft delete are planned for volatile blobs.
No full telemetry is stored in application logs. Each new question retrieves current evidence;
no persisted chat history or reuse of old grounded answers.
Service-managed retention must be reviewed before real data use.
If strict end-to-end two-hour erasure is required, reject/revise the design rather than asserting compliance.

Acceptance prompts include Tacoma vibration over 30 minutes, statewide offline devices over five minutes,
one equipment's two-hour temperature maximum, an expired-only device, and "stop the Spokane pump".
Expected outcomes are respectively exact cited statistics, explicit gaps, bounded evidence,
no fresh data, and refusal to actuate. Tacoma-only access to Spokane must return 403 even with a forged tool argument.
