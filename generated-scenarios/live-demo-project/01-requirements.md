### Agentic business workflow

Primary pattern: 01 Single-Agent Tool Loop, with the explicitly selected
17 Human-in-the-Loop overlay. The app owns the human queue and state machine;
this is not a native Foundry human-contact service.

The Foundry prompt agent receives the question and approved catalog, then calls
`select_company_answer` with an entry ID or `unsupported`.
Application policy accepts only an existing, currently approved ID.
It returns stored company wording rather than any model-generated prose.
No web, market-data or trade tool exists. A human response is labeled separately.

The simpler FAQ-only application would enforce exact wording but lose natural-language intent matching.
A generative RAG answer was rejected because grounding alone cannot guarantee no added model knowledge.
Multiple agents and a vector database add no useful outcome for the small approved knowledge catalog.

Runtime contract:

- At most one Foundry classification call per submitted question; timeout 30 seconds; input 2,000 characters.
- One recognized tool call only; unknown IDs, multiple calls and free-text-only results fail closed.
- Case transitions: automated -> waiting -> claimed -> resolved; no automatic return to AI ownership.
- Claim/reply uses optimistic concurrency; competing claims produce a conflict, not a silent overwrite.
- Repeated escalation for the same conversation returns the same case.
- Customer click, not model judgment, authorizes escalation.
- Evidence: agent response ID, source ID/version, owner and case revision; no hidden chain-of-thought.

### Network Security

Proposed private data endpoints and workload VNet integration; authenticated customer website uses public HTTPS.
An operator browser and CLI run on a private Windows management VM through Azure Bastion.
Automation must explicitly execute initialization and data-plane checks inside that VNet.
No public RDP, service keys or unrestricted data-service ingress.
