### Concrete story

Adventure Works Cycles is a fictitious mobility manufacturer for this demonstration.
Sales receives a commuter-cycle opportunity requesting a 200 km guaranteed range and a launch campaign.
The approved synthetic catalog supports only a qualified, test-condition range statement, not that guarantee.
Sales must establish product fit and uncertainties before Marketing can produce a safe, source-backed draft.

Three independently versioned Foundry prompt agents perform distinct jobs:
Sales Fit assesses the opportunity and product evidence; Marketing Claims creates an audience-specific brief
from approved claims and a sanitized Sales handoff; Handoff Coordinator reconciles both into a review packet.
The application controls the sequence, validates each handoff and exposes actual agent IDs, versions,
response IDs and source IDs. This is real multi-agent inference, not three labels on a single model response.
Human review is always required; the workload never sends a campaign or commits an order.

The finance source contributes private backend, keyless identity, APIM, signing and operational patterns.
Its brokerage content, single-agent design, source decisions and historical results do not transfer.
All app content, grounding, fixtures, prompts and tests will be new for the selected units.

### Proposed application and data contract

The app will have Opportunity, Sales Evidence, Marketing Brief and Handoff Trace views.
`POST /api/handoffs` accepts a known opportunity ID and a bounded user request; it returns the review packet.
There is no public endpoint for arbitrary tool execution, storage paths, agent selection or configuration.
Missing model/endpoint/agent configuration fails startup; local tests use explicit test doubles only.
Production execution must not contain a mock-success mode.

The new fixture set will include three product records, four opportunities and three approved claim documents.
Proposed stable IDs are `product-commuter-01`, `product-cargo-01`, `product-touring-01`,
`opp-001` through `opp-004`, and `claim-range-01`, `claim-positioning-01`, `claim-warranty-01`.
Each claim carries source version and permitted wording; all products and commercial numbers are synthetic.
`opp-001` requests an unsupported 200 km guarantee; `opp-002` fits the commuter evidence;
`opp-003` omits a required fit attribute; `opp-004` tests an unapproved product reference.
These are fixture specifications, not generated datasets or executed tests.

## Non-Functional Requirements (NFRs)

| Requirement | Proposed measurable target | Acceptance evidence |
| --- | --- | --- |
| Operational Excellence | Correlation on 100% of successful/failed stages | Trace assertions and live logs |

| Request limits | 4,000 input characters; 800 output tokens per response; 90-second total deadline | Boundary tests |

| Data minimization | Zero margin/discount/contact fields in Marketing context or final packet | Projection/leak tests |
| Reliability | Explicit dependency errors; transient retries bounded by deadline | Fault injection |
| Integrity | Signature covers canonical packet bytes and all returned provenance | Tamper test |
| Deployment repeatability | Image digest, agent versions, idempotent fixture installation | Later local/live checks |
