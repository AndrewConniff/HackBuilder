### Recommended Architecture

Browser traffic reaches a public APIM Standard v2 gateway, which serves the synthetic demo UI and API.
APIM acquires a managed identity token for a dedicated Entra backend API audience and calls the private ACA app.
The .NET 10 app runs the bounded Sales Fit -> Marketing Claims -> Handoff Coordinator pipeline.
Each step invokes a different installed Foundry prompt agent version through the new project Responses API.
The same deployed model can serve all three distinct agent definitions.

The app executes allowlisted read-only function tools against private versioned Blob fixtures.
It validates tool arguments, evidence IDs and structured handoffs before forwarding data to another agent.
The final validated draft packet is hashed and signed using a nonexportable Key Vault key.
Routine logs emit correlation IDs, stage names, durations, response IDs and token counts, not content.

Architecture and runtime PNGs will be generated after design confirmation; none exists or is claimed complete yet.

### Basic versus Standard and indispensable dependencies

Basic supports private inbound access but uses platform-managed state; it is not equivalent to the source's
customer-controlled private agent outbound/data setup.
The proposed target deliberately retains **Standard with BYO VNet**, private endpoints and disabled public data planes.
This is a target design proposal to be confirmed, not a reuse of source decisions D4/D5/D6.

Current Microsoft guidance requires BYO Storage, Cosmos DB and Search for private Standard.
They are platform file/state/vector dependencies, not discretionary Sales/Marketing business databases.
Search is not used as an additional retrieval feature; small explicit claim documents are read by bounded app tools.
No embedding model, web search, CRM, queue, Redis, agent workflow service or external connector is necessary.

ACR Premium is justified by private immutable container-image delivery, and Log Analytics by Operational Excellence.
VNet, dedicated subnets, NSGs, private endpoints and DNS are indispensable to the selected private paths.
A secretless single-tenant Entra API registration supplies a distinct APIM-to-app audience.
An installer with private network line of sight is necessary for image push, fixture upload and agent installation.
Its connection is a future deployment-preparation prerequisite, not authority to create a VPN, VM or hosted runner now.

### Business data and runtime sequence

1. The app validates the request, known opportunity ID, input size and admission limit; creates a correlation ID.
1. Sales Fit invokes `get_opportunity` and `get_product` with schema-checked identifiers.
   Tools return minimal synthetic need and product projections, not margin, discount or contact fields.
1. Sales Fit returns structured fit, constraints, unknowns and cited product IDs.
   The app verifies sources and constructs a typed Marketing handoff; it never forwards raw prompt/history.
1. Marketing Claims invokes `get_approved_claims` for known product/source IDs.
   It drafts approved positioning, flags the unsupported 200 km guarantee and preserves source wording.
1. The app validates the Marketing result, permitted claims and citations.
   Handoff Coordinator receives only sanitized Sales/Marketing structures and produces the review packet.
1. Deterministic validation enforces schema, allowed references, required caveats and `reviewRequired: true`.
   Public text is assembled from approved claim wording and validated fields, not arbitrary model-generated guarantees.
   Invalid output fails visibly; it is not repaired by inventing evidence.
1. The app signs canonical UTF-8 packet bytes, including provenance, with Key Vault RSA-2048 / PS256.
   It returns packet, digest, signature, key version and actual agent trace. The signature envelope is not self-hashed.

Sales and Marketing specialists receive distinct function allowlists and separate request/conversation contexts.
No agent gets arbitrary HTTP, file access, write tools, publication or order capabilities.
Foundry projects share agent state: three agents in one project are **not** three security-isolated departments.
This reference demonstrates application-enforced minimization over synthetic data, not production staff authorization.
Even Sales tools omit confidential fields; there is no need to trust an LLM to remove them before handing off.
Persona navigation is explicitly not authentication.

### Identity and authorization

| Principal | Proposed least-privilege access | Explicitly excluded |
| --- | --- | --- |
| Gateway MI | Backend token acquisition for unique API audience | No Foundry, fixture or signing roles |
| App MI | Project Foundry Agent Consumer; fixture-container Blob Reader | No agent creation, fixture write or admin |
| App MI | Key-scoped Crypto User; registry-scoped AcrPull | Secrets access, key management, registry push |
| Project MI | Documented Standard Storage/Search/Cosmos runtime roles | Gateway/backend API access |
| Installer principal | Project Foundry User; fixture upload, key setup, image push | Persistent app credentials |

Resolve role definitions and inspect effective permissions during authorized preparation; never guess a role GUID.
The consumer runtime identity must not be broadened to Foundry User to bypass invocation failures.
The app validates signature, issuer, lifetime, audience, tenant and the gateway MI object ID.
APIM overwrites incoming authorization for backend calls and does not trust user-supplied identity headers.
Network isolation and authorization are separate checks.

Installer caller roles differ from runtime project roles.
New capability-settings ARM `2026-07-15-preview` documentation describes caller provisioning,
while the linked private Bicep sample uses backward-compatible capability hosts/project provisioning.
The design proposes the documented private sample path, not mixing provisioning models in one template.
Implementation must recheck released AVM interfaces and exact supported resource schemas before pinning versions.
Preview ARM schema use must be explicit; core Agent Service GA does not make every API GA.

### Network and deployment boundaries

Proposed nonoverlapping address space is `10.84.0.0/16`, unrelated to the source deployment.
Subnet proposals are apps `10.84.0.0/23`, agents `10.84.2.0/24`, APIM `10.84.3.0/24`,
and private endpoints `10.84.4.0/24`. No network has been queried or allocated.
App and agent subnets are distinct and delegated to `Microsoft.App/environments`.
APIM has its own `Microsoft.Web/serverFarms` integration subnet and required NSG.

Foundry, Storage, Cosmos, Search, Key Vault and ACR disable public data-plane access and shared-key/local auth
where supported. Foundry/registry trusted-service bypass is not a substitute for private connectivity.
Private DNS covers Foundry account domains, Blob, Cosmos, Search, Key Vault, registry/data endpoints,
and the internal ACA environment wildcard/apex.
APIM outbound integration leaves its gateway public; app ingress is VNet-visible inside the internal environment.

Entra token/metadata discovery, ARM control plane, platform telemetry and dependency/base-image downloads
are explicit platform egress exceptions. This is not a zero-internet environment or firewall inspection design.
No production WAF/DDoS protection is claimed for the anonymous synthetic public surface.
New confidential-data or workforce-authentication requirements require design revision, not silent enablement.

The later authorized deployment is staged: private foundation first; private image/fixture/key/agent installation
second; workload wiring last using immutable image digest and three installed agent versions.
No public placeholder image, temporary firewall opening or copied source installation receipt is acceptable.
Private installer access must be established in preparation; absence blocks deployment, not local implementation.

### Operational behavior and recovery

Each handoff admits at most four concurrent requests per replica, with no unbounded queue.
Use a 90-second total cancellation deadline and at most seven Responses requests:
up to three each for Sales and Marketing tool loops, plus one coordinator response.
Retries count against that same maximum; no hidden unbounded retry policy.
Input is limited to 4000 characters, output to 800 tokens per response, cumulative token usage to 30,000.
Check an estimated worst-case next-call allowance before dispatch, then reconcile actual returned usage.
Model token limits and quota are distinct from application admission limits.

APIM enforces approximate per-IP and global request throttles; these are not hard spend controls.
Return 400 for invalid request, 404 for unknown fixture ID, 429 for overload, 502 for invalid/upstream agent output,
503 for an unavailable dependency and 504 for elapsed handoff deadline.
Infrastructure authentication failures return 401/403; public backend calls must fail network reachability.
All error bodies include a safe code and correlation ID without stack traces, tokens, prompts or secrets.
Do not return a completed packet if any agent, validation, grounding, tool or signing step fails.

Versioned fixture IDs and hashes, image digest, agent versions and app revision support diagnosis and rollback.
Read-only tools permit a fresh correlated retry without duplicate business writes; model text may vary between runs.
Prior failed requests must not be silently resumed or represented as successful.
Monitor per-stage failure rate, latency, usage and throttles; cap diagnostic retention/volume.
Keep any detailed demo trace separate from routine logs; display IDs and curated evidence, never chain-of-thought.
Signed bytes prove integrity, not factual correctness, business approval or suitability approval.
